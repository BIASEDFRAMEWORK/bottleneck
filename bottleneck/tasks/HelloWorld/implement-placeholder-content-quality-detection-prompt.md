# AI Implementation Prompt: Placeholder and Content Quality Detection

You are working in the `bottleneck` Go CLI repository.

Implement feature 1 from the roadmap: **Placeholder and Content Quality Detection**.

## Product Goal

Prevent a freshly initialized or weakly documented bottleneck project from appearing production-ready just because required files and section headers exist.

The current CLI validates structure. This feature must add content-quality checks so default template text and thin required sections produce warnings by default, and failures when strict mode is enabled.

## Current Architecture To Respect

Use the existing patterns instead of introducing a new reporting system.

Relevant files:

- `cmd/init.go`
  - Contains default template content created by `bottleneck init`.
- `cmd/validate.go`
  - Prints validation results from `validator.Engine`.
- `cmd/explain.go`
  - Renders validation results through `internal/explainer`.
- `cmd/scorecard.go`
  - Renders validation results through `internal/scorecard`.
- `internal/validator/engine.go`
  - Builds validators and calculates system status.
- `internal/validator/behavior.go`
- `internal/validator/intent.go`
- `internal/validator/design.go`
- `internal/validator/markdown.go`
- `internal/models/result.go`
  - Defines `ValidationResult`, `EngineResult`, `PASS`, `FAIL`, and `WARNING`.
- `internal/explainer/explainer.go`
  - Already includes validation `Message` and `Details`.
- `internal/scorecard/scorecard.go`
  - Already includes validation `Message` or `Details` as evidence.

## Required Behavior

### 1. Detect Default Template Text

Detect the exact placeholder text generated by `bottleneck init`:

- `Describe intended system behavior.`
- `Describe behavior the system must prevent.`
- `Describe required outcomes.`
- `Describe system constraints.`
- `Describe measurable success criteria.`
- `Describe system architecture.`

When any of those values are still present in their required artifact sections, return a validation warning by default.

### 2. Warn On Insufficient Required Section Content

Required Markdown sections should not pass content-quality checks when the section is empty, only contains placeholder content, or is too thin to be useful.

Implement a small Markdown helper that can inspect section bodies by heading name. Keep it simple and deterministic.

Minimum behavior:

- For `behavior/behavior-spec.md`, inspect:
  - `Expected Behavior`
  - `Unacceptable Behavior`
- For `intent/intent.md`, inspect:
  - `Outcomes`
  - `Constraints`
  - `Success Criteria`
- For `design/architecture.md`, inspect the document body after headings and detect the default placeholder.

Use conservative content heuristics:

- A required section with no non-placeholder content is insufficient.
- A required section with only one or two generic words is insufficient.
- A required section with a meaningful sentence or list item should be accepted.

Do not add AI-based quality scoring. This must be deterministic and testable.

### 3. Add Strict Mode

Add strict mode to these commands:

- `bottleneck validate --strict`
- `bottleneck explain --strict`
- `bottleneck scorecard --strict`

Default behavior:

- Placeholder or insufficient content returns `WARNING`.
- Exit code remains `0` unless another capability fails.

Strict behavior:

- Placeholder or insufficient content returns `FAIL`.
- Exit code is `1` through the existing failure path.

Prefer passing an option into `validator.NewEngine` or adding a new constructor/options struct rather than using package globals.

### 4. Show Placeholder Status Everywhere

The placeholder/content-quality result must appear in:

- `validate` output
- `explain` evidence and recommended action context
- `scorecard` text output
- `scorecard --format=json`

Use `ValidationResult.Message` and `ValidationResult.Details` so the existing renderers naturally display the result.

Warnings must identify the exact file and section needing real evidence. Example detail style:

```text
bottleneck/intent/intent.md section "Outcomes" still contains placeholder content
bottleneck/behavior/behavior-spec.md section "Expected Behavior" is too thin to validate
```

### 5. System Status Semantics

Update `internal/validator/engine.go` so warnings are visible at the system level.

Expected behavior:

- If any result is `FAIL`, `SystemStatus` is `FAIL`.
- Else if any result is `WARNING`, `SystemStatus` is `WARNING`.
- Else `SystemStatus` is `PASS`.

`PrimaryBottleneck` should remain the first failing capability when failures exist. If there are warnings but no failures, set it to the first warning capability instead of `None`.

### 6. Backward Compatibility

Do not break existing required-section validation:

- Missing files still fail.
- Empty required artifacts still fail.
- Missing required sections still fail.
- Assurance, Security, Execution, and Config behavior should remain unchanged unless system warning aggregation needs to account for their warnings.

## Testing Requirements

Add focused Go tests. Prefer temp directories and real files over brittle mocks.

Required test cases:

1. Freshly initialized template artifacts produce warnings by default.
2. Freshly initialized template artifacts produce failures in strict mode.
3. Placeholder warnings identify the exact file and section.
4. Partially completed artifacts warn only for the unchanged or insufficient sections.
5. Valid artifacts with meaningful content pass content-quality checks.
6. Engine system status becomes `WARNING` when there are warnings but no failures.
7. `validate`, `explain`, and `scorecard` paths surface the placeholder details through existing output rendering.

Test locations can include:

- `internal/validator/*_test.go`
- `internal/explainer/explainer_test.go`
- `internal/scorecard/scorecard_test.go`
- command-level tests only if the repo already has a command-test pattern; otherwise keep this at validator/rendering level.

## Implementation Guidance

Recommended approach:

1. Add a small content-quality helper in `internal/validator`, for example `content_quality.go`.
2. Add a helper to extract Markdown section text from a document.
3. Add a strict-mode option to the validation engine.
4. Update Behavior, Intent, and Design validators to append content-quality warnings/failures after structural validation succeeds.
5. Return one `ValidationResult` per capability, using `Details` for every weak section.
6. Update CLI flags to pass strict mode into the engine for `validate`, `explain`, and `scorecard`.
7. Extend tests and run `go test ./...`.

Keep the implementation deterministic, small, and consistent with the existing code style.

## Acceptance Criteria

- A freshly initialized project does not receive a clean `PASS` system status.
- Warnings identify the exact file and section that need real evidence.
- `--strict` turns placeholder and insufficient-content warnings into failures.
- Placeholder/content-quality status is visible in `validate`, `explain`, and `scorecard`.
- Tests cover unchanged templates, partially completed artifacts, and valid artifacts.
- `go test ./...` passes.
